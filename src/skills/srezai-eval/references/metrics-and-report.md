# srezai-eval — метрики, учёт фейлов, отчёт «качество × цена × латентность»

Цель отчёта — решение, а не красивое число. Поэтому сначала сырые метрики и
разброс, потом вывод; никакая композитная оценка не прячет исходную таблицу.

## 1. Статусы и знаменатель

Каждая попытка получает один статус:

| Статус | Что значит |
|---|---|
| `ok` | ответ получен, судья оценил |
| `empty` | 200, но данных нет (`empty_result`, пустая выдача) |
| `auth` | 401 / `missing_key`, `invalid_key`, `revoked_key` |
| `funds` | 402 `insufficient_funds` |
| `rate` | 429 `rate_limited` / `key_limit_reached` / `trial_limit_reached` |
| `timeout` | сетевой таймаут или `504` |
| `server` | 500/502/503 |
| `judge_fail` | ответ есть, судья не смог оценить |

Правила знаменателя:

- Знаменатель = `вопросы × конфигурации × прогоны`. **Ничего не удаляется**:
  фейл — это результат.
- Качество считается по всем пунктам: `empty`/`timeout`/`server`/`judge_fail`
  дают 0 баллов (или отдельный `unanswered`, если это решено до прогона и
  записано в манифесте).
- Доля успеха (`success_rate`) публикуется отдельной колонкой: 90 % качества
  при 60 % успеха — не «90 % качества».
- Если из-за 402 прогон неполный, это не «мало данных», а незавершённый
  эксперимент: указывается покрытие (`выполнено 42 из 180 попыток`).

## 2. Качество

- По каждому пункту — балл судьи (0–3 по критериям из
  [dataset-and-manifest.md](dataset-and-manifest.md)).
- Агрегация: среднее и медиана по пунктам; для каждой конфигурации — по прогонам.
- **Разброс:** минимум и максимум среднего по прогонам, а не только среднее.
  При ≥3 прогонах это дешёвая и честная замена доверительному интервалу.
- Разбивка по категориям (факт/сравнение/процедура/проверка/свежесть) и по
  языкам: средняя может скрывать провал в одной категории.
- Худшие 5 пунктов — в отчёт с цитатой ответа: они объясняют, что чинить.

## 3. Латентность

- Меряется вокруг вызова, включая ретраи: ретрай — часть пользовательского
  времени. Для async — от отправки до терминального статуса талона, вместе с
  интервалами опроса.
- p50 и p95 по **всем** попыткам (включая фейлы; таймаут — это максимальная
  латентность, а не пропуск).
- Формула (nearest-rank для малых выборок): отсортировать значения, взять
  элемент с индексом `ceil(p × n) − 1` (0-based).
- При `n < 20` p95 ≈ максимум: так и подписывай, не выдавай за устойчивую
  оценку. Рядом с перцентилем всегда указывай `n`.
- Отдельно можно показать «латентность успешных» — но только как дополнение,
  не вместо общей.

## 4. Цена

- Кредиты из ответа (где есть, например `credits` у `crawl`) и/или из разницы
  `get_usage` до/после — источник фиксируется в манифесте.
- `credits_per_item` = потрачено / все попытки (включая фейлы, если они стоили).
- `credits_per_success` = потрачено / число `ok`: цена за реально полученный
  результат. Обе цифры нужны: первая — бюджет, вторая — эффективность.
- Рубли: `₽ = кредиты × 0,10` (1 кредит = 0,10 ₽, `credit_rub` в
  `src/tools.json`). Смету сверяй по прайсу инструментов, а не по памяти.
- Ошибка и пустой результат не тарифицируются, но ретраи и повторные прогоны —
  тарифицируются; это видно по фактической разнице баланса.

## 5. Композитная оценка (если без неё не решают)

Порядок строгий:

1. Сырая таблица: `конфигурация | качество (mean ± min–max) | успех % | p50 | p95 | credits/item | ₽/item`.
2. Pareto-фронт: конфигурации, которые не хуже других одновременно по качеству,
   цене и латентности. Из него видно, что «дешевле и лучше» бывает.
3. Только потом — веса (`quality 0.6 / cost 0.2 / latency 0.2` — пример, а не
   догма), с явной записью в отчёт. Веса — часть решения, их согласуют с
   человеком, а не подбирают под победителя.

## 6. Правила сравнения

- Сравниваются только прогоны с одинаковыми: `dataset.sha256`, судьёй и
  промптом, каналом (CLI/MCP/REST), числом прогонов, версией API.
- Класс задачи объявляется заранее: «поиск ссылок», «готовый ответ»,
  «исследование». `deep_research` (20+ кредитов) и `web_search` (1) — разные
  продукты; сравнивать их можно только по «качество на рубль/секунду» и с
  оговоркой.
- Разрыв меньше разброса между прогонами — **ничья**, а не победа.
- Победитель не выбирается по лучшему прогону: бери среднее (или медиану) по
  всем прогонам.
- Holdout не используется для настройки; если использовал — это уже dev, и
  нужен новый holdout.
- Провайдеры с разными возможностями (цитаты, async-талон, лимиты) сравниваются
  только по общим критериям; различия выносятся в «чего нет».

## 8. Как читать отчёт

- p95 важнее p50 для пользователя: редкие 30-секундные ответы помнят дольше,
  чем быстрые.
- `credits_per_success` важнее `credits_per_item`, когда много фейлов.
- Разница в качестве меньше разброса — не трать деньги на «победителя».
- Любая цифра без `n`, даты и манифеста — не результат, а мнение.
