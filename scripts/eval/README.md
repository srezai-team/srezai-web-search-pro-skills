# Оценка качества веб-поиска — воспроизводимый harness

Этот каталог — запускаемый harness для сравнения srezai с другим web-поиском на
одинаковом датасете. Он закрывает слабые места прошлого прогона
(`kitay-postavki/compare/srezai-vs-tavily.md`): один прогон, экспертные оценки без
листа, Tavily через прокси, нет манифеста и учёта фейлов.

Контракт (по образцу `parallel-search-evaluation`):

```
positions.json → run.mjs (manifest + traces + метрики) → grade.mjs (судья) → summary.md
```

Что фиксируется на каждом шаге: датасет, конфигурация и лимиты — в манифесте;
сырые ответы и тайминги — в трассах; латентность p50/p95, фейлы, стоимость — в
метриках; оценки 0–10 — в листе судьи с обоснованием.

---

## Быстрый старт

```bash
# 1. План прогона без сети и без ключа (по умолчанию — dry-run).
node scripts/eval/run.mjs

# 2. Живой прогон: ключ только из окружения, три повтора — методический минимум.
SREZAI_API_KEY=... node scripts/eval/run.mjs --live --repeats 3

# 2а. Дымовой прогон без ключа: анонимный пробный режим srezai
#     (25 запросов/сутки на IP, только --repeats 1). Проверяет интеграцию
#     end-to-end, но НЕ является методической оценкой.
node scripts/eval/run.mjs --trial --limit 15 --run-id smoke-$(date -u +%Y%m%d)

# 3. Опционально: второй провайдер тем же датасетом.
SREZAI_API_KEY=... BASELINE_URL=https://api.example.com/search BASELINE_KEY=... \
  node scripts/eval/run.mjs --live --repeats 3 --providers srezai,baseline

# 4. Лист оценок для человека по последнему прогону.
node scripts/eval/grade.mjs --judge-sheet

# 5. Заполнить CSV и применить оценки: grades.json + пересобранный summary.md.
node scripts/eval/grade.mjs --apply

# Самопроверка harness (dry-run, артефакты, отсутствие ключа, .gitignore).
bash scripts/eval/test-dry-run.sh
```

`--help` у обоих скриптов работает без сети и без ключа.

## Переменные окружения

| Переменная | Зачем | Обязательна |
|---|---|---|
| `SREZAI_API_KEY` | ключ srezai для `--live` | да, для `--live` |
| `SREZAI_BASE_URL` | база REST, по умолчанию `https://srezai.ru` | нет |
| `BASELINE_URL` | endpoint второго провайдера | для baseline |
| `BASELINE_KEY` | ключ второго провайдера → `Authorization: Bearer` | нет |
| `BASELINE_NAME` | имя провайдера в отчёте (по умолчанию `baseline`) | нет |
| `BASELINE_BODY` | JSON-шаблон тела с подстановкой `{{query}}`, `{{num}}`, `{{depth}}`, `{{language}}`; подставляются JSON-значения, поэтому в шаблоне кавычек вокруг плейсхолдеров нет | нет |

Пример `BASELINE_BODY` под чужой API с другими именами полей:

```bash
BASELINE_BODY='{"query":{{query}},"max_results":{{num}},"search_depth":"advanced"}' \
BASELINE_URL=https://api.example.com/search BASELINE_KEY=... \
  node scripts/eval/run.mjs --live --providers srezai,baseline
```

**Ключи.** Значение ключа читается только из env, никогда не печатается и не
попадает в артефакты: в манифест пишется лишь `set`/`unset`, в команду —
отмаскированная строка, в сообщениях об ошибках значения вырезаются. Не передавай
ключ аргументом командной строки — он останется в истории shell.

## Артефакты прогона

```
scripts/eval/runs/<UTC>/
  manifest.json     что именно запускали: harness, дата, датасет, конфигурация,
                    провайдеры, лимиты, цены; mode=dry-run|live; network=skipped|performed
  results/<id>.json по позиции: запрос, все попытки и повторы, латентность каждого
                    HTTP-вызова, нормализованные результаты и сырой ответ провайдера
  summary.json      метрики в машинном виде: по провайдерам, языкам, интентам; фейлы;
                    пересечение доменов; блок quality после grade.mjs
  summary.md        человекочитаемый отчёт (русский)
  judge-sheet.csv   лист оценок: строка = позиция × провайдер, три колонки 0–10
  grades.json       применённые оценки с комментариями и агрегатами
```

`runs/` **не коммитится**: это временные данные прогонов, они могут содержать
большие сырые ответы и зависят от времени. Исключение задано в
`scripts/eval/.gitignore`; для публикации прикладывай артефакты к отчёту отдельно.

## Датасет

`positions.json` — 25 позиций, ровно те же формулировки, что в прогоне
13.11.2026 (P01–P25), чтобы новые прогоны были сравнимы с опубликованными.
Поля: `id`, `query`, `language` (`ru`/`en`/`zh`), `intent`
(`fact`/`list`/`compare`/`factory`), `notes` — подсказка судье, что считать хорошим
ответом.

Распределение: **en 18, ru 3, zh 4**; интенты: list 13, factory 7, fact 4,
compare 1. Тема — закупки/фабрики/рынки Китая. Китайские и русские позиции —
намеренная проверка языковых сегментов, а не равные по объёму срезы.

Язык позиции — только срез отчётности. Провайдер получает один и тот же параметр
`language` (по умолчанию `auto`): srezai принимает `auto|ru|en`, китайский язык
серверу не передаётся, поэтому zh-позиции проверяют именно кросс-языковую выдачу.

## Методика

### 1. Один прогон — снимок, а не измерение

Поиск зависит от кэша, нагрузки движков, свежести индекса и реранкера. Минимум —
**3 повтора** (`--repeats 3`) в один временной срез. Сравнивать прогоны между собой
можно только близкие по времени: выдача и латентность меняются.

Как агрегировать:

- латентность — по всем успешным попыткам (повторы пулятся), p50/p95 считаются
  nearest-rank по объединённой выборке;
- качество — судья оценивает **первый повтор** каждой позиции, чтобы не смешивать
  разные срезы выдачи; разброс между повторами фиксируется отдельно (сырые трассы
  лежат рядом);
- стоимость — успешные вызовы × цена; ошибки и пустые ответы не списываются.

### 2. Латентность

p50/p95 считаются по формуле nearest-rank:

```
p = sorted[ceil(q * n) - 1],  q = 0.50 / 0.95
```

Только по успешным вызовам: таймауты и ошибки не входят в перцентили, они
считаются отдельно (`failed`, `timeouts`). При малом `n` p95 — это фактически
максимум: на 25 попытках p95 = 2-е значение сверху. Для устойчивого p95 нужно
≥100 запросов; в отчёте это написано прямо.

`--concurrency 1` по умолчанию: параллельные запросы искажают латентность.
Поднимай concurrency только для прогонов, где важна длительность, и фиксируй это
в манифесте.

### 3. Фейлы: провайдер vs harness

| Ситуация | Классификация | Кто виноват | Влияние |
|---|---|---|---|
| Таймаут по нашему `--timeout-ms` | `timeout` | провайдер/сеть | фейл прогона, код 1 |
| HTTP 5xx, 429 | `http` | провайдер/инфраструктура | фейл прогона, код 1 |
| HTTP 401/402 | `http` | ключ/баланс (конфигурация) | фейл прогона, код 1 |
| HTTP 400 | `http` | параметры запроса/harness | фейл прогона, код 1 |
| DNS/connection refused | `network` | сеть или окружение | фейл прогона, код 1 |
| Ответ не JSON | `parse` | провайдер нарушил контракт | фейл прогона, код 1 |
| Битый датасет, неизвестный флаг, нет ключа | — | harness | код 2, прогон не начат |
| Плохая релевантность выдачи | не фейл | качество | влияет на оценку, не на код |

Коды возврата: `0` — успех (dry-run всегда), `1` — live-прогон с инфраструктурными
фейлами (артефакты всё равно пишутся), `2` — ошибка использования/конфигурации.
Плохая релевантность никогда не даёт ненулевой код: это работа судьи, а не сбой.

### 4. Что сравнивать можно, а что нельзя

Фиксируй одинаковыми: датасет, `num` (top-10/top-5 при оценке), язык, таймаут,
retry policy, concurrency, окно времени.

Нельзя выдавать за равное сравнение:

- разные настройки провайдеров «как каждый умеет лучше» (например, srezai `auto`
  за 1 кредит против платного advanced-режима) — это отдельный режим, его надо
  назвать в манифесте;
- разные `num`, язык или фильтры у провайдеров;
- baseline через прокси/гео-обход — латентность завышена, а качество может
  отличаться от прямого доступа; пиши это в ограничениях;
- один прогон против другого без близкого времени и одинаковой конфигурации.

В манифесте сохраняется всё, что нужно для повторения: провайдер, endpoint (без
query), контракт запроса, лимиты, параметры, цена и источник цены.

### 5. Судья и рубрика

`grade.mjs --judge-sheet` пишет CSV: по строке на пару (позиция, провайдер),
top-5 заголовков и ссылок, `notes` из датасета и три колонки оценок:

| Оценка | Диапазон | Что значит |
|---|---|---|
| `score_relevance_0_6` | 0–6 | релевантность топ-5: 0 — мимо, 6 — все пять результатов по делу |
| `score_specificity_0_2` | 0–2 | конкретика: адреса, цены, MOQ, даты вместо общих слов |
| `score_usability_0_2` | 0–2 | пригодность: можно ли ответить на вопрос или начать действие |
| `score_total_0_10` | 0–10 | сумма; можно оставить пустой — посчитается |

`--apply` проверяет диапазоны, дубли, неизвестные строки и полноту (неполный лист
принимается только с `--allow-partial`), пишет `grades.json` и пересобирает
`summary.json`/`summary.md` с таблицей «качество × латентность × стоимость».

Правила честной оценки:

- один и тот же оценщик и одна рубрика для всех провайдеров; при LLM-судье —
  одна модель, один prompt, одинаковая температура, и ≥20 % строк проверяет
  человек по оригиналу;
- порядок строк стоит перемешать между провайдерами (в CSV есть колонка
  `provider` — по умолчанию оценка не слепая; для слепой скрой/переименуй
  провайдера вручную перед оценкой);
- спорные оценки и обоснование — в колонку `comment`, иначе оценка не
  воспроизводима;
- фейлы не оцениваются: доступность измеряется числом успешных попыток, а не
  нулём за качество.

### 6. Как публиковать результат

Публикуй вместе: `manifest.json`, `summary.md`, `grades.json`, сырые ответы (или
хотя бы top-5) и лист оценок. В тексте отчёта указывай: дату и время, конфигурацию,
число позиций и повторов, p50/p95 с размером выборки, число фейлов, стоимость и
раздел ограничений. Не называй это бенчмарком при n < 100 и не ранжируй
провайдеров по одному прогону. Вывод формулируй по задачам: «нашёл ли источник»,
«дал ли контекст», «подтвердил ли факт» — а не «модель лучше».

## Ограничения метода

Этот harness честно воспроизводит методику, но не снимает её ограничений:

1. **Датасет узкий и не сбалансирован.** 25 позиций по одной теме (закупки в
   Китае), без holdout и без отрицательных примеров. Результат нельзя переносить
   на общий веб-поиск. Китайских позиций всего 4 — это проверка дыры, а не
   представительная выборка языка.
2. **Оценки субъективны.** Рубрика снижает разброс, но судья — человек или LLM.
   При одном оценщике нет межэкспертной надёжности; LLM-судья требует ручной
   сверки. Оценка 0–10 по top-5 — прокси качества, а не nDCG по gold-разметке.
3. **Нет gold-разметки.** Мы не знаем полный пул релевантных документов, поэтому
   recall не измеряется. Метрики — про выдачу, а не про полноту веба.
4. **p95 неустойчив на малых n.** 25–75 наблюдений дают p95 ≈ максимум; доверительных
   интервалов нет, сравнение провайдеров по латентности при n < 100 — только
   «порядок величины».
5. **Сравнение настроек.** Провайдеры могут сравниваться в своих лучших режимах
   (разная цена и разный объём работы). Это допустимо, если записано в манифесте,
   но такие числа нельзя складывать с сопоставимым режимом.
6. **Внешние условия.** Живой прогон зависит от сети, гео, нагрузки и кэша;
   baseline через прокси искажает латентность. Повторяемость между днями не
   гарантирована, воспроизводим сам метод, а не выдача.
7. **Стоимость известна не для всех.** Для srezai цена берётся из `src/tools.json`
   и считается по успешным вызовам; цена baseline не известна harness и должна
   задаваться вручную.
8. **Свежесть и даты публикаций** измеряются только как доля результатов с датой
   (`published_date_share`), а не как «актуальность факта». Проверка фактов
   (даты, цены, адреса) — отдельный шаг, который этот harness не делает.
9. **Первый повтор не равен остальным.** Судья оценивает один повтор; если
   выдача между повторами сильно расходится, оценка качества смещена. Разброс
   виден по сырым трассам, но в сводку не агрегируется.
10. **Слепоты нет по умолчанию.** CSV содержит имя провайдера; для слепой оценки
    его надо переименовать/скрыть вручную.

## Структура каталога

```
scripts/eval/
  positions.json       датасет 25 позиций (RU/EN/ZH), версионируется
  run.mjs              прогон: dry-run по умолчанию, --live, артефакты и метрики
  grade.mjs            лист судьи (--judge-sheet) и применение оценок (--apply)
  lib.mjs              общие функции: перцентили, CSV, маскирование ключей, summary.md
  test-dry-run.sh      самопроверка без сети и без ключа
  .gitignore           runs/ не коммитится
  README.md            этот документ
```

## Что осталось на живой прогон

В репозитории harness проверен на dry-run и на локальном stub-провайдере (живой
сетевой прогон в тестах не выполнялся). Перед публикацией результата нужно:

1. задать `SREZAI_API_KEY` и прогнать `--live --repeats 3`;
2. при сравнении с конкурентом — задать `BASELINE_URL`/`BASELINE_KEY` (прямой
   доступ, не прокси) и прогнать оба провайдера одним датасетом в одном срезе;
3. заполнить `judge-sheet.csv` и применить оценки;
4. сверить p50/p95 с числом наблюдений и перенести ограничения из отчёта в
   публикацию.
