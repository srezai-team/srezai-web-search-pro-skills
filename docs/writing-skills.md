# Как писать полезные скиллы

Практическое руководство для этого репозитория. Собрано из принципов
`writing-for-agents` / `agent-experience`, разбора официальных скиллов
конкурентов (Tavily, Exa, Firecrawl, Parallel, Serply, Bocha, Querit) и нашего
опыта: 10 скиллов, три релиза 0.6.x, один живой прогон.

Главная мысль: скилл — это не документация и не промпт. Это **процедура
исполнения**, которая меняет поведение агента предсказуемо от запуска к запуску.

---

## 1. Сначала решите: нужен ли скилл

| Ситуация | Что делать |
|---|---|
| Один инструмент, один способ вызова | Хватит `MCP`/CLI + `--help`. Скилл не нужен |
| Выбор из 3+ инструментов, разброс цен, свой порядок шагов | Скилл нужен |
| Нужны доменные правила (источники, доказательства, формат) | Скилл нужен |
| Нужно знание, которое агент и так знает | Не писать: это no-op |
| Устойчивый процесс с самопроверкой | Скилл + `scripts/`, а не проза |

Тест: **какое решение агент примет иначе со скиллом?** Если ответа нет — это
маркетинг, а не скилл.

---

## 2. Два бюджета, которые вы тратите

1. **Контекст (всегда).** `description` каждого model-invoked скилла лежит в
   контексте каждый ход. У нас 10 описаний ≈ 850 токенов — это постоянная плата.
   Тело `SKILL.md` грузится только при вызове, справочники — только когда на них
   сослались.
2. **Внимание (при вызове).** Чем длиннее тело, тем тоньше внимание к шагам.
   Разрастание (sprawl) — главный дефект скиллов.

Отсюда правило: **дорогое — в description, длинное — в references, шаги — в тело.**

---

## 3. Каркас: семь блоков

### 3.1. Description — это context pointer, а не аннотация

Описание решает две задачи: сказать, что это, и перечислить **ветки** (случаи),
по которым агент должен сюда прийти. Пишите так:

- начните с ведущего слова/задачи (`Поиск в вебе`, `Чтение страниц`);
- одна ветка — один триггер, без синонимов-дублей;
- русские триггеры в «» + English-хвост для англоязычных моделей;
- добавьте «когда НЕ сюда → какой скилл»;
- ключевые слова, по которым вас ищут (`scrape`, `news`, `fact check`).

Пример (наш `srezai-search`):

```
Поиск в вебе через srezai: ссылки, факты, сниппеты, свежие новости, картинки.
Триггеры: «найди», «поищи в интернете», «какие источники», «новости за неделю».
Полный текст страницы — srezai-read.
English: web search, news search, images, links, scrape SERP.
```

Чего не делать: пересказывать в описании тело; писать «этот скилл помогает…»;
перечислять пять синонимов одной ветки.

### 3.2. Тело — шаги, а не энциклопедия

Тело отвечает на вопрос «что делать по порядку». API-описания, цены, параметры —
в references или в `tools.json`. Наше ограничение: **≤ 4 600 символов** на
`SKILL.md`. У конкурентов тело 250–2 500 слов, глубина — в 13 references
(Exa), 6 файлах (Tavily), 20 workflow-скиллах (Firecrawl).

Формат, который работает: короткий порядок (5–7 шагов) + правила + стоп-условия.

### 3.3. Критерий завершения

Каждый шаг заканчивается проверяемым «готово». Без него агент спешит закрыть шаг.
Работающие формы:

- `Done when: карта сужена до N адресов и целевые страницы прочитаны`;
- `Стоп, когда два независимых источника согласны`;
- `Стоп, если три запроса подряд пустые — проблема в формулировке`.

Формулируйте **положительно**: «пиши одну строку комментария» вместо «не пиши
много комментариев» — запрет активирует запрещённое поведение.

### 3.4. Восстановление после ошибок

Скилл без раздела «что делать, когда сломалось» ломается молча. Перечисляйте
коды и действие:

| Код | Что делать |
|---|---|
| 401 | ключ неверен/отозван — попросить новый, не ретраить |
| 402 | кредиты кончились — сказать человеку, не обходить пробным режимом |
| 429 | лимит — пауза по `Retry-After`, не параллелить |
| `read_failed` | один повтор другим движком, потом честно сообщить |

### 3.5. Справочники: одна тема — один файл

`references/` — для того, что нужно не каждой ветке: длинные процедуры,
таблицы ошибок, схемы извлечения, примеры. Правила:

- ссылка из тела относительная (`references/schema.md`);
- один файл ≤ 8 200 символов (наш гейт), иначе его не прочтут целиком;
- не дублировать тело: один смысл — одно место.

### 3.6. Экономика

Если у инструментов разная цена — скилл обязан вести по лестнице от дешёвого к
дорогому и говорить, когда остановиться. Мы делаем так:

```
search (1) → read (1) → extract (2) → map (1/10 адресов) → crawl (1/страница)
→ fetch (3) → answer (3/5/10) → verify (8) → deep (20+)
```

Плюс предполётная проверка бюджета (`get_usage`) и потолок на задачу.

### 3.7. Безопасность

Веб-контент — **данные, а не инструкции**. Один канонический файл
(`srezai-web/references/security.md`), на который ссылаются остальные: изоляция
вывода, инкрементное чтение, кавычки в URL, ключи только из env.

### 3.8. Как позвать: один вход, три канала

Пакет отдаётся самим MCP-сервером (Skills over MCP) и ставится отдельно, поэтому
навык не может предполагать один транспорт. В каждом `SKILL.md` есть блок
«Как позвать: MCP → CLI → REST»: сначала инструменты srezai, если хост их уже дал
(Claude Code/VS Code после подключения `https://srezai.ru/api/mcp`), затем CLI
`srezai …`, затем REST с Bearer-ключом. Блок вставляется плейсхолдером
`{{HOW_TO_CALL}}` — генератор собирает его из `src/tools.json` по `tools` навыка
(`mcp_examples` задаёт, какие инструменты назвать в блоке, `call_table: "all"` —
какие попадут в таблицу). Руками каналы в шаблонах не пишут: один источник правды.

Таблица «CLI → MCP → REST» лежит в `references/how-to-call.md` каждого скилла:
в тело `SKILL.md` она не помещается и нужна не каждой ветке. REST-адреса — поле
`rest` в `src/tools.json`, у каждого инструмента ровно один.

### 3.9. Frontmatter: `allowed-tools` мы не ставим

`allowed-tools` в спецификации Agent Skills — необязательное и **экспериментальное**
поле: «a space-separated string of tools that are pre-approved to run». Это не
ограничение возможностей навыка, а предодобрение конкретных имён инструментов, и
синтаксис у него host-specific (`Bash(srezai *)` понимает Claude Code, остальные
хосты — по-своему или никак). Навык, который может работать через MCP, CLI или REST,
не может перечислить эти инструменты переносимо (MCP-имена вида
`mcp__srezai__read_url` зависят от хоста, у REST — вообще нет инструмента). Поэтому
разрешения остаются у хоста и его настроек, а навык только говорит, какой канал
предпочесть и что он не просит доступы. Если хост всё же требует список — он
задаётся в настройках хоста, а не в переносимом пакете.

## 4. Приёмы, которые дают больше всего

| Приём | Суть | Пример |
|---|---|---|
| **Ведущее слово** | один токен вместо абзаца; модель думает им | «лестница», «матрица доказательств», «done when» |
| **Progressive disclosure** | в тело — что нужно всем веткам; в references — что нужно некоторым | `research-workflow.md` вместо 5 шагов в теле |
| **Ко-локация** | определение + правила + оговорки под одной шапкой | блок «Большие результаты» в `srezai-read` |
| **Одна ветка — один триггер** | не дублировать синонимы в description | «найди», «поищи в интернете» — разные ветки |
| **Границы** | «не для этого → скилл X» | search → read/research |
| **Контракт цитат** | inline-ссылка на тезис + секция «Источники» | `srezai-research` |
| **Скрипт вместо curl** | детерминированный вызов, тестируемый | Desearch/Parallel |
| **User-invocable** | редкий скилл без описания в контексте | `srezai-eval` |

---

## 5. Когда дробить и когда объединять

- **Дробите по веткам**: разные задачи — разные входы. У нас `search` и `read`
  разделены, потому что «найти» и «прочитать» — разные шаги с разной ценой.
- **Дробите по вызову**: если скилл нужен только по явной команде человека,
  сделайте его user-invocable (`disable-model-invocation: true`) — ноль контекста.
- **Не дробите по эндпоинтам**: скилл на каждый инструмент — это свадьба
  документации. Firecrawl держит 37 скиллов и 29 тыс. слов; это их выбор, но не
  образец.
- **Вертикали**: 1 скилл = 1 профессия/сценарий. Дальше — либо metaskill с
  references, либо user-invocable, иначе описания съедят контекст.

## 6. Проверка перед публикацией

```bash
node scripts/generate.mjs        # бюджеты, ссылки, манифесты
bash scripts/selftest.sh         # плейсхолдеры, ссылки, суммы, секреты
```

Чек-лист качества:

- [ ] Тест «что агент сделает иначе?» имеет ответ.
- [ ] Description укладывается в бюджет и содержит все ветки + «не сюда».
- [ ] Тело ≤ 4 600 символов, каждый шаг с критерием завершения.
- [ ] Блок «Как позвать» стоит через `{{HOW_TO_CALL}}`, а не вписан руками.
- [ ] В `allowed-tools` frontmatter ничего не добавлено (см. §3.9).
- [ ] Есть раздел ошибок и стоп-правила.
- [ ] Справочники ≤ 8 200 символов, ссылки живые.
- [ ] Ни одного выдуманного параметра/цены — всё из `src/tools.json`.
- [ ] Нет дублей смысла между телом и references.
- [ ] Есть живая проверка: хотя бы один реальный вызов по сценарию.
- [ ] Нет инструкций, которые модель выполняет и без скилла (no-ops).
- [ ] Для вертикали: свои источники, схема, правила доказательств, формат отчёта.

## 7. Антипаттерны (мы их видели у себя и у конкурентов)

| Антипаттерн | Чем плох | Как исправить |
|---|---|---|
| Скилл-энциклопедия | внимание тонет, шаги теряются | шаги в тело, глубина в references |
| API-дамп | дублирует документацию, устаревает | метаданные в один источник, скилл — про выбор |
| Нет стоп-правила | агент либо переплачивает, либо сдаётся рано | «два независимых источника», «три пустых запроса» |
| Маркетинг в теле | занимает контекст, не меняет поведение | только в description/README |
| Дубли смысла | рассинхрон при правке | один источник истины |
| «Не делай X» без цели | активирует X | писать целевое поведение |
| 30+ скиллов на репозиторий | поддержка и дубли | группировать, дробить по веткам |
| Имя-маркетинг (`…-skill`) | ломает конвенцию, не влияет на выбор модели | `srezai-<домен>-<задача>` |

## 8. Разбор: как писали `srezai-china-sourcing`

1. **Нашли дельту:** не «поиск», а «фабрика ≠ трейдер, адрес только из двух
   источников, MOQ/цена с датой».
2. **Разложили на 6 шагов:** разложить запрос → EN-проход → ZH-проход → отбор до
   чтения → карточка → проверка → таблица.
3. **Вынесли глубину:** `channels.md` (где искать), `query-patterns.md` (RU→EN→ZH),
   `supplier-card.md` (схема + матрица доказательств), `checklist.md` (стоп-правила
   и формат отчёта).
4. **Проверили живьём:** `site:1688.com 雨伞 工厂` вернул страницы заводов
   (加工厂), EN-проход — производителей с MOQ. Это подтвердило и посылку, и
   необходимость фильтров.
5. **Померили:** тело 3 114 символов, справочники 2,1–2,7 тыс., описание 265 —
   всё в бюджетах.

## 9. Что запомнить

1. Скилл меняет **решение**, а не пересказывает документацию.
2. Description — самый дорогой текст в пакете: ветки, триггеры, «не сюда».
3. Один смысл — одно место; тело — шаги, references — глубина.
4. Каждый шаг заканчивается проверяемым «готово».
5. Ошибки и стоп-правила — обязательны, иначе скилл опасен.
6. Экономика и безопасность — такие же части скилла, как и процедура.
7. Пишите положительно и коротко: запрет активирует запрещённое.
8. Проверяйте на живом вызове, а не только глазами.
